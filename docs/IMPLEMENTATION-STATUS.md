## Automatic protection backup before Windows updates or removal — 2026-10-31

**Status:** Implemented in Windows version `0.2.21`. The uninstaller now makes a timestamped snapshot of the local PGlite database, local runtime/connection configuration, existing backups, and hardware/terminal settings before it removes an installed Nabta version. A matching install-time fallback protects upgrades from legacy installers that did not contain the hook.

- Snapshot location: `Documents\\Nabta Backups\\pre-install\\Nabta-pre-install-<timestamp>`.
- The installer/uninstaller stops rather than proceed if the required backup cannot be created. Incomplete copies are never marked with a manifest as valid snapshots.
- Verified with a synthetic PGlite directory and configuration fixture, `pnpm --filter @nabta/desktop package:win`, and package inspection confirming the PowerShell backup tool is bundled.

# إصدار Windows 0.2.35 — عزل انقطاع الإنترنت عن الكاشير المحلي — 2026-11-07

**الحالة:** منفّذ ومتحقق منه ومضمّن في حزمة Windows.

- أصبح تشغيل قاعدة نبتة المحلية هو شرط جاهزية نقطة البيع الوحيد. يبدأ نفق Cloudflare كخدمة اختيارية في الخلفية بعد جاهزية الخادم المحلي، فلا ينتظر البرنامج DNS أو الإنترنت أو اتصال Cloudflare قبل أن يفتح أو يقبل البيع والبحث.
- إذا توقف نفق Cloudflare بسبب الإنترنت، يعيد نبتة محاولته تدريجيًا في الخلفية حتى خمس دقائق بين المحاولات؛ لا يعيد تشغيل قاعدة البيانات المحلية ولا يوقف البيع أو الفاتورة المفتوحة.
- شارة أعلى البرنامج توضح الآن «البيانات المحلية جاهزة» بدل إيحاء أن الإنترنت هو المقصود بكلمة «متصل». فقد الإنترنت وحده لا يعطّل هذه الحالة.
- اختبار تشغيل يدوي بعد التثبيت: افصل الإنترنت من الجهاز الرئيسي، افتح نبتة، سجّل الدخول، ابحث عن صنف وأصدر فاتورة نقدية؛ يجب أن تنجح العملية محليًا. أعد الإنترنت لاحقًا للتحقق من عودة النفق دون إعادة تشغيل نبتة.
- التحقق المنفذ: `pnpm --filter @nabta/desktop typecheck` ناجح، وبناء `pnpm --filter @nabta/desktop package:win` ناجح. فحص حزمة Windows أكد وجود الخادم المحلي في مساري الحزمة والترحيلات `40/40`.

# ترقية Cloudflare — نسخة سحابية محمية قابلة للتحديث — 2026-11-07

**الحالة:** منفّذ ومنشور ومتحقق منه، لكنه ليس بعد نواة معاملات مالية كاملة.

- أصبحت نواة Cloudflare تحتفظ بمؤشر منفصل لآخر نسخة سحابية تم التحقق منها. يبدأ رفع النسخة التالية في مساحة مرحلية؛ وتبقى الكتالوجات والبيانات المقروءة من آخر نسخة سليمة متاحة أثناء الرفع.
- لا يتحول المؤشر إلى النسخة الجديدة إلا داخل معاملة SQL واحدة بعد التحقق من عدد السجلات وبصمة كل جدول وبصمة النسخة الاحتياطية. فشل الرفع أو انقطاع الإنترنت لا يحذف النسخة السحابية السابقة ولا يجعل الكتالوج فارغًا.
- يعيد برنامج Windows الآن إعداد نسخة محلية حديثة عند كل تحديث سحابي مكتمل، ولا يعيد رفع manifest قديم. بعد أول ربط ناجح لا يحتاج التحديث الدوري مفتاح التهيئة أو تغيير كلمة مرور المالك.
- تم إنشاء Bucket مستقل `nabta-pos-backups` في R2 وربطه بالـWorker. بعد اعتماد كل نسخة داخل Durable Objects تُؤرشف manifest ودفعاتها إلى R2. فشل R2 لا يلغي النسخة المعتمدة؛ تبقى الأرشفة بالحالة `PENDING` لتُستكمل لاحقًا بدل فقد البيانات أو تعطيل الكاشير.
- تم نشر Worker `nabta-cloud-core` على Cloudflare بالإصدار `bf70b689-bd98-4690-9d6c-fac815e78d98`، وفحص `GET /v1/cloud/health` أكد الوضع `CLOUD_PROTECTED_REPLICA` والتخزين `durable-object-sqlite`.
- الحدود المقصودة: المبيعات، الوارد، المرتجعات، الديون وخصم المخزون ليست بعد معاملات سحابية معتمدة. تبقى نقطة البيع المحلية تعمل أوفلاين، وتستمر عملية الصلاحية السحابية المؤمنة فقط مع تسوية صريحة إلى الجهاز الرئيسي. لا يجوز تحويل التطبيقات إلى بيع مالي مباشر على Worker قبل تنفيذ المرحلة التالية واختبارات التعارض والتسوية.
- التحقق المنفذ: `pnpm --filter @nabta/contracts build` ناجح، `pnpm --filter @nabta/desktop typecheck` ناجح، `npx wrangler deploy --dry-run` ناجح قبل كل نشر، ثم `npx wrangler deploy` ناجح. تم التحقق من رابط الصحة بعد النشر؛ أول أرشفة R2 فعلية ستتم مع أول تحديث سحابي جديد من الجهاز الرئيسي.
